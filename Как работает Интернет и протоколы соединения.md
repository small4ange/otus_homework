# 1. Что такое Интернет

Интернет — это огромное количество компьютеров, соединенных между собой большой паутиной - сетью.

Каждый компьютер имеет свой адрес - например:
```
95.163.32.11
```

Это IP-адрес. Когда браузер хочет открыть сайт, он сначала должен узнать IP сервера.

---

# 2. Что такое домен

Людям неудобно запоминать IP, поэтому придумали домены, например:

```
google.com
```

На самом деле браузер делает так:

```
google.com
      ↓
DNS
      ↓
142.250.74.78
```

DNS - это телефонная книга Интернета. Она переводит имя сайта в IP. Получив IP, браузер знает, куда отправлять запрос.

---

# 3. Что такое IP

IP отвечает только за одно: доставить пакет нужному компьютеру.
IP не знает:
- что внутри пакета;
- получил ли его сервер;
- потерялся ли он.
Он просто пытается доставить. Поэтому поверх IP работают другие протоколы.

---
# Транспортные протоколы над IP
## 1. TCP

TCP - транспортный протокол.
Его задача:
- установить соединение;
- гарантировать доставку;
- восстановить потерянные пакеты;
- соблюдать порядок.
Например отправляем

```
1
2
3
```

Если пакет №3 потерялся
TCP скажет

```
повтори пакет 3
```

Пока пакет не придет, приложение ничего не получит. Поэтому HTTP работает через TCP.

---

## 2. UDP

UDP - тоже транспортный протокол намного проще. Он говорит

```
Вот пакет.
Лови.
```

Никаких гарантий. Если пакет потерялся —

```
ну и ладно
```

Используется там, где скорость важнее.

Например
- видеозвонки;
- онлайн игры;
- IPTV;
- стриминг;
- DNS.
Лучше потерять один кадр, чем ждать его секунду.

---

## TCP vs UDP

TCP

✔ надежный

✔ подтверждает получение

✔ следит за порядком

✔ медленнее

UDP

✔ очень быстрый

✖ может потерять данные

✖ порядок не гарантируется

# Socket

Многие думают, что socket — протокол, но нет.
Socket — это интерфейс операционной системы.

Представь телефон. TCP — это телефонная сеть. Socket — это трубка телефона, через которую разговаривает программа.

PHP

```
$socket = socket_create(...);
```

Node

```
net.Socket()
```

Java

```
Socket socket
```

TCP и UDP — это правила передачи данных. Сокет — это объект, через который программа использует эти правила.

## Что происходит внутри операционной системы

Допустим, PHP хочет отправить HTTP-запрос.
Он не может сказать ядру:
> "Эй, TCP, отправь вот это."
Вместо этого он вызывает системные функции:

```
socket_create()
socket_connect()
socket_write()
socket_read()
```
И операционная система создает **сокет**.
Этот сокет становится "точкой подключения" программы к сетевому стеку.
Получается такая цепочка:

```
PHP
   │
socket
   │
TCP
   │
IP
   │
Интернет
```

---

## Что хранит сокет

Когда создается сокет, он хранит информацию о соединении.
Например:

```
локальный IP
192.168.1.15

локальный порт
54321

удаленный IP
142.250.74.78

удаленный порт
443

протокол
TCP
```

То есть сокет — это не просто функция.
Это объект, который описывает конкретное сетевое соединение.

---

## Почему нельзя без сокета?

Потому что TCP обслуживает **тысячи соединений одновременно**.
Например:
У тебя открыт Chrome.
В нем:

```
YouTube
Google
GitHub
StackOverflow
Telegram Web
```

Все работают через TCP.
Как операционная система понимает, какое сообщение относится к какому сайту?
Она хранит отдельный сокет для каждого соединения.
Например:

```
Socket #1
192.168.1.15:50123
→ youtube.com:443

Socket #2
192.168.1.15:50124
→ github.com:443

Socket #3
192.168.1.15:50125
→ google.com:443
```

Каждый сокет имеет свое состояние и свои буферы.

---

## Почему HTTP-программисты редко работают с сокетами?

Потому что это уже сделал кто-то другой.
Например, в PHP ты пишешь:

```
file_get_contents("https://google.com");
```

или

```
curl_exec($curl);
```

или

```
Guzzle
```

Кажется, что сокетов нет.
Но внутри происходит примерно следующее:

```
Guzzle
    ↓
cURL
    ↓
socket()
    ↓
TCP
    ↓
IP
```

То есть библиотека сама создает сокет.

---

## А когда программист создает сокеты сам?

Когда пишет приложения, которым недостаточно обычного HTTP:
- чат;
- игровой сервер;
- прокси;
- VPN;
- SSH-клиент;
- FTP-сервер;
- собственный сетевой протокол.
Например, простой TCP-сервер на PHP:
```
$socket = socket_create(AF_INET, SOCK_STREAM, SOL_TCP);
socket_bind($socket, "0.0.0.0", 8080);
socket_listen($socket);
```
Здесь ты уже напрямую работаешь с TCP через сокет.

# Прикладные протоколы над IP 
## WebSocket

**WebSocket** — это прикладной протокол для постоянного двустороннего обмена данными между браузером и сервером.
### HTTP vs WebSocket

Допустим, у тебя открыт чат Telegram в браузере. Ты пишешь:

> Привет

Браузер делает запрос:

```
POST /sendMessage
```

Сервер отвечает:

```
200 OK
```

На этом всё. Соединение закрывается. Через секунду приходит сообщение от друга. Как браузер узнает об этом? По HTTP есть только один вариант — **самому постоянно спрашивать сервер**.

```
Есть новые сообщения?

Нет.

Есть новые сообщения?

Нет.

Есть новые сообщения?

Да.
```

Получается куча лишних запросов.
Решение - WebSocket. WebSocket позволяет открыть соединение **один раз** и держать его открытым.

```
Браузер
     │
═══════════════════════
     │
Сервер
```

Соединение не закрывается. Теперь обе стороны могут отправлять данные **в любой момент**. Не нужно ждать нового HTTP-запроса.
HTTP работает по принципу:

```
Клиент
    ↓
Запрос
    ↓
Сервер
    ↓
Ответ
```

После ответа соединение обычно завершается или простаивает до следующего запроса.
WebSocket:

```
Клиент
 ⇅
Сервер
```

Любая сторона может первой отправить сообщение.

---

### Как открывается WebSocket

Интересно, что начинается всё с обычного HTTP. Браузер отправляет запрос:

```
GET /chat HTTP/1.1

Upgrade: websocket
Connection: Upgrade
```

Тем самым он говорит:
> "Давай перестанем разговаривать по HTTP и перейдем на WebSocket."

Если сервер согласен:

```
101 Switching Protocols
```

После этого HTTP заканчивается.
Дальше идет уже протокол WebSocket поверх того же TCP-соединения.
Получается:

```
WebSocket
      ↓
TCP
      ↓
IP
```

---

### Где используют WebSocket

Практически везде, где данные должны приходить мгновенно.
Например:
- 💬 чаты (Telegram Web, Discord, Slack)
- 📈 биржевые котировки
- 🎮 онлайн-игры
- 📹 совместное редактирование документов (Google Docs)
- 🔔 уведомления
- 📊 панели мониторинга (Grafana)
- ⚽ трансляции счета матчей
- 🚕 отслеживание такси на карте

---

### Почему тогда не использовать WebSocket всегда?

Потому что он имеет свои особенности.
Для обычного сайта:

```
открыть страницу

получить HTML

получить CSS

получить JS
```

WebSocket вообще не нужен.
HTTP здесь проще, дешевле и лучше поддерживается инфраструктурой (кэширование, CDN, балансировщики и т.д.).
Поэтому используют правило:
- **HTTP** — когда клиент сам запрашивает данные время от времени.
- **WebSocket** — когда серверу нужно иметь возможность отправлять данные клиенту сразу после появления события.

---

## HTTP

HTTP — прикладной протокол.
Он определяет как клиент должен разговаривать с сервером.
Например

```
GET /users HTTP/1.1
Host: site.ru
```

Сервер отвечает

```
200 OK

JSON
```

HTTP не умеет шифровать. Любой может прочитать запрос.
### Как работает HTTP

HTTP состоит из двух частей:
1. **Запрос (Request)** — клиент → сервер.
2. **Ответ (Response)** — сервер → клиент.
Например:

```
GET /users/15 HTTP/1.1
Host: example.com
```
Ответ:
```
HTTP/1.1 200 OK
Content-Type: application/json

{
    "id": 15,
    "name": "Иван"
}
```

---

### Структура HTTP-запроса

```
GET /users/15 HTTP/1.1
↑     ↑
│     URL
│
Метод
```

Далее идут заголовки:

```
Host: example.com
Authorization: Bearer token
Content-Type: application/json
Accept: application/json
```

И затем (не всегда) тело запроса.

---

### HTTP-методы

#### GET
Получение данных.
Ничего не изменяет на сервере.

```
GET /users
```

Ответ:

```
[
  {"id":1},
  {"id":2}
]
```

Используется для получения данных от сервера.

---

### POST

Создание нового объекта.

```
POST /users
```

Тело:

```
{
    "name":"Иван"
}
```

Ответ:

```
201 Created
```

Используется при:
- регистрация;
- создание заказа;
- создание пользователя.

---

### PUT

Полностью заменяет ресурс. Например до:

```
{
  "name":"Иван",
  "age":20
}
```

Отправляем

```
{
  "name":"Петр",
  "age":25
}
```

После:

```
{
  "name":"Петр",
  "age":25
}
```

Все поля считаются новой версией объекта.

---

### PATCH

Частичное изменение. До:

```
{
  "name":"Иван",
  "age":20
}
```

Отправляем

```
{
   "age":21
}
```

Получаем

```
{
  "name":"Иван",
  "age":21
}
```

Используется намного чаще PUT.

---

### DELETE

Удаляет объект.

```
DELETE /users/15
```

Ответ

```
204 No Content
```

или

```
200 OK
```

---

### HEAD

То же самое что GET, но без тела ответа.

Используется для проверки:
- существует ли файл;
- размера файла;
- даты изменения.

Например

```
HEAD image.jpg
```

Ответ:

```
200 OK
Content-Length: 155621
```

---

### OPTIONS

Спрашивает сервер какие методы доступны.
Ответ

```
Allow:
GET
POST
DELETE
```
Очень используется CORS. 
##### **CORS (Cross-Origin Resource Sharing)**
**CORS** — это механизм безопасности браузера, который определяет, **можно ли JavaScript-коду с одного сайта отправлять запросы на другой сайт**.
**CORS — это не протокол**, а механизм, реализованный браузерами поверх HTTP.

---

### TRACE

Возвращает обратно запрос. Используется для диагностики. Практически всегда отключен.

---

### CONNECT

Используется прокси-серверами. Например при HTTPS. Обычные разработчики почти никогда с ним не работают.

---

### Идемпотентность методов

Идемпотентность означает:

> повторный одинаковый запрос приводит к тому же результату.

Например

```
DELETE /users/15
```

Первый раз: удалили пользователя.
Второй раз: его уже нет.
Состояние не меняется.
DELETE считается идемпотентным.

---

|Метод|Идемпотентный|
|---|---|
|GET|✅|
|PUT|✅|
|DELETE|✅|
|HEAD|✅|
|OPTIONS|✅|
|POST|❌|
|PATCH|Обычно ❌|

---

### HTTP-ответ

Ответ состоит из

```
HTTP/1.1 200 OK
```

где 200 - код ответа

## HTTPS

HTTPS = HTTP + TLS
или
HTTPS = HTTP + SSL

На практике сейчас используется именно TLS. SSL считается устаревшим.

То есть

```
HTTP
↓
TLS
↓
TCP
↓
IP
```

Данные становятся зашифрованными.

---

### SSL и TLS

Раньше использовался SSL. Сейчас используется TLS. SSL уже небезопасен. 
#### Что делает TLS

Ты заходишь на сайт без HTTPS:

```
http://example.com
```

Ты отправляешь логин и пароль.
По сети летит примерно это:

```
POST /login

login=katrina
password=123456
```

Все это передается **в открытом виде**.
Любой человек, который находится в этой же сети и умеет анализировать трафик (например, с помощью Wireshark), сможет увидеть содержимое пакетов.

```
Твой компьютер
      │
      │ login=katrina
      │ password=123456
      ▼
Wi-Fi роутер
      ▲
      │
Хакер тоже подключен к этой сети
```

Именно эту проблему решает TLS.
TLS добавляет между HTTP и TCP дополнительный уровень защиты. 
Без TLS:
```
HTTP
 ↓
TCP
 ↓
IP
```
С TLS:
```
HTTP
 ↓
TLS
 ↓
TCP
 ↓
IP
```

Теперь HTTP-запрос сначала шифруется, а уже потом отправляется.
Вместо этого:
```
POST /login

password=123456
```
По сети летит что-то вроде:
```
9A 7F C1 D3 54 8B 1E ...
```
Даже если пакет перехватят, прочитать его нельзя без ключа.

**Но возникает проблема** шифрования - допустим, браузер и сервер умеют шифровать, но как они договорятся **каким ключом** шифровать? Нельзя просто отправить ключ через Интернет.
Если отправить:
```
Вот мой ключ:

123456789
```
То злоумышленник тоже его увидит.
Поэтому TLS использует комбинацию двух видов криптографии:
#### Симметричное шифрование
Представь сейф. У тебя есть ключ. У сервера есть точно такой же ключ.
```
ключ
 ↓
шифрование

тот же ключ
 ↓
расшифровка
```
Например:
```
Ключ

abc123
```
Шифруем
```
password
```
Получаем
```
XQ9#@!A...
```

Такое шифрование очень быстрое.
Поэтому почти весь HTTPS-трафик после установки соединения использует именно симметричное шифрование (например, AES или ChaCha20).
Но остается вопрос:

> **Как безопасно передать этот общий ключ?**

#### Асимметричное шифрование
Для этого используется пара ключей.
```
Публичный ключ

можно раздать всем

↓

Приватный ключ

хранится только на сервере
```
Представь почтовый ящик. Любой может бросить письмо внутрь. Но открыть ящик может только владелец. Именно так работает публичный ключ.
Сервер говорит:
```
Вот мой публичный ключ.
```
Его могут увидеть все. Ничего страшного.
Браузер берет случайно сгенерированный симметричный ключ.
Например
```
8F93D2...
```
Шифрует его публичным ключом сервера.
Получается
```
AB8DFF998...
```
Теперь даже если злоумышленник перехватит сообщение, он увидит только зашифрованный вариант. Расшифровать его сможет **только сервер**, потому что только у него есть приватный ключ.
После этого и браузер, и сервер знают один и тот же симметричный ключ.
Теперь весь дальнейший трафик шифруется уже этим ключом.
Почему?
Потому что симметричное шифрование **в десятки и сотни раз быстрее**, чем асимметричное.
Поэтому асимметричная криптография используется только для безопасного обмена ключами (или подтверждения личности), а не для шифрования всего трафика.
#### Откуда браузер знает, что это настоящий сервер?
Вот здесь появляется сертификат.
Допустим, ты открываешь
```
https://google.com
```
Сервер отвечает:
```
Вот мой сертификат.
```

В сертификате указано:
- домен (`google.com`);
- публичный ключ;
- срок действия;
- кто выдал сертификат;
- цифровая подпись удостоверяющего центра (CA).
#### Кто выдает сертификаты?
Существуют доверенные удостоверяющие центры (Certificate Authority, CA).
Например:
- Let's Encrypt;
- DigiCert;
- GlobalSign;
- Sectigo.
Они проверяют владение доменом и подписывают сертификат своим приватным ключом.
#### Почему браузер им верит?
В операционной системе и браузере уже есть список доверенных удостоверяющих центров.
Получается такая цепочка:

```
Windows / Chrome
↓
Доверяет Let's Encrypt
↓
Let's Encrypt подписал сертификат
↓
Значит сертификату можно доверять
```

Если подпись не сходится или сертификат просрочен — браузер показывает предупреждение.
#### Что такое TLS Handshake
Перед началом обмена данными браузер и сервер проводят процедуру, которая называется **TLS Handshake** (рукопожатие).
Упрощенно она выглядит так:
**Шаг 1**
Браузер:
```
Привет.
Я умею TLS 1.3.
Поддерживаю такие алгоритмы.
```
**Шаг 2**
Сервер:
```
Отлично.
Я тоже умею TLS 1.3.
Вот мой сертификат.
```
**Шаг 3**
Браузер проверяет:
- сертификат подписан доверенным CA;
- срок действия не истек;
- домен совпадает;
- цепочка доверия корректна.
Если что-то не так - соединение не устанавливается.
**Шаг 4**
Браузер и сервер безопасно договариваются об общем симметричном ключе (в современных версиях TLS обычно с помощью алгоритма обмена ключами ECDHE).
**Шаг 5**
Теперь начинается обычный HTTP, но весь он уже зашифрован.

#### Три главные задачи TLS

##### 1. Конфиденциальность (Confidentiality)
Никто не сможет прочитать данные.
```
логин
пароль
cookie
JSON
API
```
Все зашифровано.
##### 2. Целостность (Integrity)
Допустим, злоумышленник решил изменить пакет.
Ты отправил
```
{
  "sum":100
}
```
Он попытался заменить на
```
{
  "sum":100000
}
```
TLS обнаружит изменение с помощью криптографических механизмов проверки целостности (в современных шифрах это обычно встроенная аутентификация данных).
Соединение будет разорвано.
##### 3. Подлинность (Authentication)
Ты уверен, что разговариваешь именно с сервером банка, а не с мошенником. Это обеспечивает сертификат и проверка его доверенной подписи.

## SSH

SSH - отдельный прикладной протокол.
Используется для удаленного управления сервером.
Например

```
ssh user@server
```

Можно
- выполнять команды;
- копировать файлы (SCP, SFTP);
- настраивать сервер;
- создавать SSH-туннели.
Работает поверх TCP.
### Настройка SSH-туннеля
Программы для Windows для подключения по SSH-туннелям:
Putty - одна из самых удобных программ:
![[Pasted image 20260721143816.png]]
Подключение по SSH-туннелю на Linux:
`ssh root@212.67.14.86`
### Аутентификация в SSH

- приватный ключ - должен храниться только на хостовом компьютере и никогда не передаваться и не копироваться на другие машины. Его ни в коем случае нельзя никому показывать. В PuTTY этот файл имеет расширение `.ppk`
- публичный ключ - Его можно свободно копировать и размещать на всех серверах, к которым вы хотите подключаться.

Когда вы пытаетесь подключиться к серверу, он "проверяет" ваш приватный ключ с помощью сохранённого публичного. Если они подходят друг к другу, доступ разрешается без ввода пароля

### Опции конфигурации SSH в файле /etc/ssh/ssh_config

- PermitRootLogin - определяет возможно ли зайти через пользователя root. Но для безопасности его обычно отключают
- PasswordAuthentication - определяет разрешена ли аутентификация по паролю SSH-ключей
- PubKeyAuthorization - позволяет использовать публичный ключ для подключения
- MaxAuthTries - макс кол-во подключений
- AllowUsers - юзеры которым разрешено подключение

### Что такое SSH-туннель и его преимущества
 ![[Pasted image 20260721150212.png]]

**SSH-туннель** - это зашифрованный канал связи, который создаётся между вашим компьютером и удалённым сервером через протокол SSH. Весь трафик, проходящий через этот канал, шифруется, что обеспечивает конфиденциальность и защиту данных.

Простыми словами: вы создаёте "защищённый трубопровод" через интернет, по которому можно безопасно передавать любые данные, даже если сам протокол передачи небезопасен.

---

### Как это работает?

SSH-туннель перенаправляет сетевой трафик с определённого порта на одном компьютере на порт на другом компьютере через зашифрованное SSH-соединение.

[Ваш компьютер] ---(SSH-шифрование)---> [SSH-сервер] ---> [Целевой сервер]
      (локальный порт)                  (шлюз)              (например, RDP:3389)

---
### 📊 Типы SSH-туннелей

|Тип|Ключ|Направление|Описание|
|---|---|---|---|
|**Локальный (Local)**|`-L`|Ваш ПК → Удалённый сервер|Перенаправляет порт с вашего ПК на удалённую машину через SSH-сервер|
|**Удалённый (Remote)**|`-R`|Удалённый сервер → Ваш ПК|Перенаправляет порт с удалённого сервера на ваш ПК|
|**Динамический (Dynamic)**|`-D`|SOCKS-прокси|Создаёт SOCKS-прокси, через который можно направлять любой трафик|

### Примеры комманд:

#### 1. Local Port Forwarding (-L)
Команда:

```
ssh -L 8080:internal-server:80 user@gateway
```
```
8080                 ← локальный порт на твоем ПК

internal-server:80  ← куда попасть после SSH

user@gateway        ← SSH-сервер
```

Получается схема
```
Браузер
    │
localhost:8080
    │
════════ SSH ════════
    │
gateway
    │
internal-server:80
```

То есть ты открываешь
```
http://localhost:8080
```
а реально попадаешь на
```
internal-server:80
```

##### Где используют Local Tunnel

###### 1. Подключение к БД
Есть PostgreSQL

```
10.0.0.5:5432
```

Она доступна только внутри сети компании. Снаружи ее открыть нельзя. Но есть SSH-сервер. Тогда

```
ssh -L 5432:10.0.0.5:5432 user@gateway
```

Теперь DBeaver подключается

```
localhost:5432
```

а реально работает с удаленной БД.

###### 2. Открыть внутренний сайт

Например

```
Jenkins

http://10.0.0.15:8080
```

Из дома его открыть нельзя. Делаешь

```
ssh -L 8080:10.0.0.15:8080 user@gateway
```

Теперь

```
localhost:8080
```

открывает Jenkins.

###### 3. PhpStorm

Очень часто IDE подключается именно так.

```
PhpStorm
↓
localhost
↓
SSH
↓
Удаленная БД
```

#### Remote Port Forwarding (-R)
Это противоположная ситуация. Команда

```
ssh -R 9000:localhost:3000 user@public-server
```

Схема

```
Интернет
     │

     │

```


##### Что происходит

У тебя локально работает
```
React

localhost:3000
```
Но никто его не видит. Ты открываешь туннель. Теперь любой, кто откроет

```

```

##### Где используют

###### Демонстрация проекта

Например, локально работает

```
localhost:3000
```

Заказчик сидит в другом городе. Вместо деплоя делаешь

```
ssh -R 80:localhost:3000 VPS
```

И заказчик уже видит твой сайт.
###### Webhook
**Вебхук (Webhook)** — это способ, при котором один интернет-сервис автоматически и мгновенно отправляет данные (обычно через HTTP-запрос) другому сервису при наступлении какого-либо события. Это механизм мгновенных оповещений «на лету», работающий по принципу: _«Если что-то произошло, сразу отправь информацию туда»_.
Очень популярный пример.
- Stripe
- GitHub
- Telegram
умеют отправлять webhook только на публичный IP. Но сервер у тебя локально. Делаешь

```
GitHub
↓
VPS
↓
SSH
↓
localhost
```

Теперь webhook приходит к тебе.
###### Обход NAT
Допустим, компьютер находится за домашним роутером. Подключиться к нему нельзя. Но он сам может подключиться к VPS. Тогда через Remote Tunnel можно получить доступ к этому компьютеру извне.

#### Dynamic Port Forwarding (-D)

Команда

```
ssh -D 1080 user@server
```

Здесь не указывается конечный сервер, потому что его выбирает программа сама.
SSH превращается в **SOCKS-прокси**. Получается

```
Chrome
      │
SOCKS 1080
      │
════ SSH ════
      │
SSH сервер
      │
Любой сайт Интернета
```

##### Что такое SOCKS
SOCKS — это протокол прокси. Он говорит

```
Я хочу открыть
google.com
443
```
или
```
github.com
443
```
или
```
reddit.com
443
```

SSH получает этот запрос и уже сам открывает соединение.

##### Где используют
 1. **VPN "на минималках"**
Очень распространенный случай. В Firefox указываешь

```
SOCKS
127.0.0.1
1080
```
Теперь весь браузер ходит через SSH-сервер.
 2. **Обход ограничений**
Например нужно, чтобы браузер выходил в Интернет через сервер в другой стране. SSH это делает.
 3. **Тестирование**
Например ты хочешь проверить как сайт открывается из Германии. Поднимаешь VPS в Германии. Делаешь
```
ssh -D 1080 germany-vps
```
Весь браузер теперь работает через немецкий сервер.

### ✅ Главные преимущества SSH-туннелей

 1. 🔒 **Безопасность и шифрование**
SSH шифрует весь трафик, проходящий через туннель. Это защищает данные от перехвата (man-in-the-middle атак), особенно в небезопасных сетях (публичный Wi-Fi, интернет-кафе).
 2. 🚧 **Обход файрволов и ограничений**
Туннель позволяет обходить сетевые фильтры и брандмауэры, которые блокируют определённые порты или протоколы. Вы можете получить доступ к сервисам, которые не доступны напрямую.
 3. 🛡️ **Защита "небезопасных" протоколов**
Даже если вы используете незащищённый протокол (например, HTTP, FTP, Telnet, VNC), через SSH-туннель весь трафик становится зашифрованным.
 4. 🔑 **Единая точка входа**
Вы можете организовать доступ к целой внутренней сети через один SSH-сервер (шлюз), не открывая множество портов в интернет.
 5. 📁 **Передача файлов**
Через туннель можно безопасно передавать файлы с помощью SCP или SFTP.
 6. 🌍 **Анонимность**
Использование SSH-туннеля как SOCKS-прокси позволяет скрыть ваш реальный IP-адрес, делая вас анонимным в сети.

### 🧠 Сценарии использования

| Сценарий                                                     | Тип туннеля         | Пример                                                                                                             |
| ------------------------------------------------------------ | ------------------- | ------------------------------------------------------------------------------------------------------------------ |
| **Подключение к RDP-серверу** через интернет                 | Локальный (`-L`)    | `ssh -L 3389:target:3389 user@gateway` → RDP-клиент подключается к `localhost:3389`                                |
| **Доступ к веб-панели роутера** за VPN                       | Локальный (`-L`)    | `ssh -L 8080:192.168.1.1:80 user@gateway` → открываем в браузере `localhost:8080`                                  |
| **Доступ к локальному веб-серверу** из интернета             | Удалённый (`-R`)    | `ssh -R 80:localhost:3000 user@public-server` → внешние пользователи заходят на `public-server` и видят ваш сервер |
| **Анонимный серфинг** в интернете                            | Динамический (`-D`) | `ssh -D 1080 user@server` → настраиваем браузер на SOCKS-прокси `localhost:1080`                                   |
| **Безопасное подключение к базе данных** (MySQL, PostgreSQL) | Локальный (`-L`)    | `ssh -L 3306:db-server:3306 user@gateway` → подключаемся к `localhost:3306`                                        |

### ⚠️ Важные нюансы

- **Скорость**: туннель немного замедляет соединение из-за шифрования/дешифрования данных.
- **Зависимость**: туннель работает, пока активно SSH-соединение. Если оно прервётся — туннель пропадёт.
- **Настройка сервера**: на SSH-сервере должно быть разрешено порт-форвардинг (опция `AllowTcpForwarding yes` в `/etc/ssh/sshd_config`).
- **Двойной туннель**: можно создавать цепочки туннелей для обхода многоуровневых ограничений (`ssh -J` или `ProxyCommand`).
- Можно передавать файлы

# SOAP

SOAP — это протокол обмена сообщениями, который обычно работает поверх HTTP.
SOAP всегда использует XML.
Например
```
<Envelope>
   <Body>
      ...
   </Body>
</Envelope>
```
Очень популярен в банках, государственных системах и старых корпоративных интеграциях.

REST

- быстрее

# VPN

VPN — это технология создания защищенного туннеля через Интернет.

Без VPN

```
ПК
 ↓
Интернет
 ↓
Сервер
```

С VPN

```
ПК
 ↓
Зашифрованный туннель
 ↓
VPN сервер
 ↓
Интернет
 ↓
Сервер
```

Интернет видит только зашифрованный трафик до VPN-сервера.

VPN может использовать разные протоколы (например, WireGuard, OpenVPN, IPsec), поэтому сам по себе VPN — не один конкретный протокол.

# Как открывается сайт

Теперь соберем всё вместе.

Ты открываешь

```
https://google.com
```

Происходит следующее:

1. Браузер спрашивает DNS:
    - «Какой IP у google.com?»
2. DNS отвечает:
    - `142.250.x.x`
3. Браузер устанавливает TCP-соединение с этим IP.
4. Затем выполняется TLS-рукопожатие: сервер доказывает свою подлинность с помощью сертификата, стороны договариваются о ключах шифрования.
5. После установки защищенного соединения браузер отправляет HTTP-запрос внутри TLS:

```
GET /
```

6. Сервер отвечает HTML.
7. Затем браузер запрашивает CSS, JavaScript, изображения и другие ресурсы.

|TLS|современный протокол защиты соединения|
|Socket|программный интерфейс ОС для работы с сетью|
