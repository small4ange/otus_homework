# Свойства PHP

- PHP написан на языке C
- PHP является компилируемым ЯП, несмотря на то что компиляция происходит в промежуточные бинарные файлы (opcode) и далее интерпретируется виртуальной машиной (Zend Engine)
- PHP имеет слабую динамическую типизацию
#### Типизация в ЯП

>- **Статическая:** Типы всех переменных известны **до запуска программы**, на этапе компиляции. Если в переменную для чисел попытаться записать текст, код просто не скомпилируется.

>- **Динамическая:** Типы определяются **во время работы программы**. Переменная может сначала хранить число, а потом текст.

>- **Строгая (сильная):** Язык **не разрешает** автоматически складывать или сравнивать разные типы данных. Если сложить число `5` и строку `"5"`, будет ошибка.

>- **Слабая (нестрогая):** Язык **сам пытается** превратить один тип в другой, если вы их смешиваете. Например, `5 + "5"` превратится в число `10` или в строку `"55"`.

Но хорошей практикой для PHP является написание 
```
declare(strict_types=1);
```
В начале каждого файла - включает строгую типизацию во избежание ошибок.

### Этап 2. Синтаксический анализ

Допустим у нас есть:
- выражение x = 2 + 5 * 10
- фраза Have I told you to stay put?
Если мы превратим их в массив токенов и вычислим выражение по порядку или переведем фразу слово за словом, то получим совершенно неверный ответ.

Представим что наш массив токенов - длинное математическое выражение, а чтобы расставить в нем скобки, другими словами **сгруппировать операции**

Таким образом в каждом языке (даже в PHP) есть определенные грамматические правила, которые описывают структуру **высказываний**

#### Форма Бэкуса-Наура
Грамматика в языках программирования прописывается с помощью **формы Бэкуса-Наура**

#### Как работает в PHP
- Для PHP существует своя грамматика языка (https://phplang.org/spec/19-grammar.html)
- программа GNU Bison берет эту грамматику и генерирует парсер
- парсер применяет грамматику к массиву токенов
- в результате получаем AST
#### AST - Абстрактное синтаксическое дерево 
- корень - самое начало программы
- каждый узел - отдельная операция
- дочерние узлы - аргументы операции
![[Pasted image 20260730104444.png]]

Дерево любого ЯП можно посмотреть тут: https://astexplorer.net/
- Тернарный оператор - оператор, у которого 3 дочерних узла
```
$a == 10 ? 1 : 2
```
- Унарный оператор - у кого 2 дочерних узла (2 операнда)
В результате 2 этапа PHP разобрался, какие операции упоминаются в коде, сгруппировал операции в нужном порядке. Теперь нужно сделать так, чтобы эти операции запустились на компьютере.
##### Особенности AST
- можем представить программу в виде дерева, не привязанного к языку программирования
- дерево можно превратить обратно в программу, но на любом другом языке (Ассемблер например)
- точно также работают многие программы для машинного перевода
##### Оптимизация AST
- удалить недостижимые ветви
- заранее подсчитать какие-то выражения

### Этап 3. Компиляция

1. У нас есть дерево с исходным кодом и мы знаем, что оно соответствует **синтаксису** языка (слова в предложениях идут в нужном порядке). Теперь нужно проверить его **семантику** (что выражения имеют смысл).
2. Нужно превратить дерево в набор инструкций для виртуальной машины Zend Engine, которая умеет выполнять эти специальные инструкции - **опкоды**
#### Как это работает в PHP:
- PHP рекурсивно обходит AST в несколько проходов
- при этом выполняется оптимизация дерева
- в итоге компилятор превращает дерево в набор опкодов
Для каждой функции готовится:
- массив опкодов
- доп информация о переменных, которые в ней используются 
#### Опкоды
- выполняют сравнительно простые операции
- порядок выполнения строго по очереди
- для циклов и условных выражений используются опкоды, напоминающие GOTO (**Goto** - это оператор безусловного перехода в программировании, который передает управление в другую точку программы, указанную меткой, «go to» = перейти к).

![[Pasted image 20260730115135.png]]
JMPZ - операция как GOTO - если условие проходит, то переходим на 4 строчку
Язык похож на язык ассемблера

Опкоды сделаны такими простыми, чтобы их можно было как и ассемблер проще перевести в машинный код (команды для процессора)
Использование перевода в опкоды позволяет запустить код на любом процессоре (даже на утюге)
## 2. Выполнение программы (runtime - время выполнения)

Непосредственно работа программы на процессоре, когда она готова к запуску.

#### Что необходимо для работы программы?
- команды, которые она будет выполнять
- данные, которые она будет обрабатывать
- память, где это все будет размещаться
### Модель памяти
#### Выделение памяти
- PHP обычно может обрабатывать несколько запросов (PHP FPM например управляет несколькими процессами) - для каждого запроса запускается отдельный процесс, на который выделяется оперативная память.

На выполнение такой программы например
```
echo "Hello, world!";
```
требуется **2МБ оперативной памяти**, потому что на старте всегда выделяется фиксированный размер оперативки - размер чанка = 2 МБ. Если памяти не хватит, PHP попросит дополнительную память, выделенную в виде **чанка** (1 чанк примерно 2МБ).

Процесс не может получить доп память когда либо в .ini файле указан memory_limit и он исчерпан, либо когда кончилась оперативка на компьютере.

### Как создаются переменные в PHP?
- у каждой переменной есть тип и значение, которые потом могут измениться
- значит, переменная может внезапно стать больше по размеру
- а слева и справа в памяти уже лежат другие переменные
Для хранение переменных в памяти используется особая структура данных (16 байт) - **zval**:
- под значение выделено 8 байт
- небольшие значения (целые числа) хранятся прямо **внутри** zval
- более крупные значения (строки и массивы) хранятся **отдельно** (на куче), а в zval лежит **указатель** на них (адрес в памяти)
```
$b = 20; //int
// выделяется 16 байт под zval
// тип IS_LONG
// значение 20

$b = "Очень длииииинная строкаааа"; //string
// zval занимает 16 байт
// в нем меняется тип IS_STRING
// на куче выделяется память под длинную строку
// значение zval содержит указатель на кучу - адрес в памяти
```
### Работа с массивами

- в массиве каждый элемент - это zval

#### Потребление памяти в массивах
- по умолчанию создается массив из 8 элементов
- когда заполняются все элементы - размер массива удваивается (опять степени двойки)
- даже если элементы из массива удаляются (методом unset) - размер массива не уменьшается (php это просто не умеет)
- память вернется только если сделать unset($array) - то есть всего массива


### Сборка мусора

Часть довольно объемных данных хранится в куче. В отличие от стека кучу нельзя просто очистить, так как на один объект может ссылаться несколько переменных из разных мест программы

![[Pasted image 20260730134359.png]]
Очищаем объект из стека (ссылку на него)
![[Pasted image 20260730134456.png]]
Объект пользователя не удалится, так как на него могут ссылаться другие переменные
#### Как работает сборка мусора в PHP:
- на куче лежат **контейнеры**: строки, массивы и объекты и пр.
- ссылки на контейнеры (указатели) хранятся в переменных zval
- для каждого контейнера заводится счетчик **refcount** с кол-вом ссылок на контейнер
- когда счетчик обнуляется - PHP удаляет контейнер с кучи - чистит мусор

Для отображения занимаемой памяти можно использовать функцию - позволяет отдебажить приложение и понять какую память занимает та или иная переменная:
```
xdebug_debug_zval('название_переменной');
```

Когда у нас имеется циклическая ссылка ($a ссылается на $b, а $b ссылается на $a) если мы удалим переменные - в памяти их refcount будет >0 и память от объекта не очистится.
![[Pasted image 20260730140004.png]]
Берем класс Spiderman() с полями real и clones[] 
Создаем настоящего Spiderman 
Создаем 10_000 клонов с ссылкой real = настоящий Spiderman
А настоящий Spiderman будет хранить ссылку clones[] = 10_000 клонов созданных нами
![[Pasted image 20260730140832.png]]
Получаем, что у нас есть 10_000 клонов ссылающихся на один объект Spiderman и один объект Spiderman, ссылающийся на массив из 10_000 клонов
Итого на объект в памяти Spiderman refcount=10_001 ссылка и 11 МБ памяти занято
Теперь берем и удаляем настоящего Spiderman и удаляем последнего клона, который остался после цикла создания клонов методом unset(). Причем настоящий Spiderman и клон - переменные, смотрим через x_debug_zval - переменных нет, а память как занимала 11 МБ так и занимает.
![[Pasted image 20260730140942.png]]
Получается мы удаляем человека паука, но тк все клоны ссылались на него - объект из памяти не удалится так как у объекта refcount != 0
![[Pasted image 20260730141047.png]]
А теперь мы удаляем клона, переменная удалится, а на объект из памяти будет ссылаться не до конца удаленный настоящий человек паук - опять refcount !=0 у объекта клона. Поэтому память и не очистилась.
Для очистки таких циклических ссылок используется одна функция в PHP:
```
gc_collect_cycles();
//показать кол-во удаленных ссылок:
echo gc_status()['collected'];
```
И память становится чистенькой
### Кэширование опкодов
![[Pasted image 20260730143604.png]]
Много времени уходит на то чтобы при каждом запуске скрипта заново его компилировать в опкоды, хотя сам скрипт при этом не меняется.

Для решения данной проблемы в PHP есть механизм OPcache:
![[Pasted image 20260730143835.png]]
- при первом запуске скрипта он компилируется как обычно
- опкоды, полученные при компиляции сохраняются в кэш
- при последующих запусках скрипта вместо компиляции берутся готовые опкоды из кэша
- чтобы проверить нужно ли обновлять кэш OPcache хранит даты последних изменений в файлах
### Предзагрузка (PHP 7.4+)
В PHP 7.4 появилась предзагрузка (Preloading):
- кэш опкодов создается сразу после старта PHP (еще до первого запроса)
- таким образом, кэш прогревается заранее
- прирост производительности при этом до 25%

### JIT (PHP 8.0+) - Just in time компиляция
Мы научились кэшировать опкоды, но нам все равно нужно выполнить их в виртуальной машине PHP, поэтому в PHP 8.0 появился **JIT-компилятор** - кэш для машинного кода, который потом прокидывается на ЦП.
Таким образом для выполнения определенных операций нам даже не нужна виртуальная машина
- прирост производительности небольшой
![[Pasted image 20260730145126.png]]
В какой-то степени наша программа превращается в готовый exe-шник или PHP превращается в C - выполнение сразу на ЦП.

JIT не дает эффекта для веб приложений, потому что приложения в основном получает данные из БД или внешних ресурсов, не занимаясь особенной математикой на процессоре.

# Сравнение PHP с другими ЯП

## C/C++
- компилируется сразу в машинный код
- есть возможность скомпилировать в язык ассемблера
- скомпилированный код (exe-шник) будет работать только на тех CPU под которые он компилировался
## Java
- компилируется в байт-код
- этот байт-код можно перенести на любое устройство, где есть JVM (виртуальная машина Java) и запустить его там
- архитектура CPU принципиально ни на что не влияет

## LISP
- один из древнейших языков
- код похож на нагромождение скобочек
- по сути каждая программа - это уже готовое дерево
- используется в машинном обучении, в ИИ, в разборе текстов и в LLM-моделях
