## Apache
![[Pasted image 20260805171931.png]]
-  Возник в 1995г и в он был монополистом
- Раньше была архитектрура DenWer = PHP + Apache + MySQL
- Потом появились LAMPP = Linux + Apache + MySQL + PHP
- .htaccess нужен для того чтобы Apache понимал куда идти при обработке запроса: пришел запрос -> apache пошел в директорию, указанную в конфиге -> нашел директорию .htaccess -> относительно данного файла понимал куда ему нужно отправлять запросы
- Когда была необходимость сделать единую точку входа - отправлять на все запросы на index.php - нужно было .htaccess класть в директорию вместе с index.php и больше ничего туда не класть, потому что иначе бы не работала единая точка входа
- Apache и PHP стали популярными за счет того, что единый вебсервер мог обслуживать сразу несколько доменов и можно было с одной железки обслуживать несколько доменов
- Тяжелый потому что у него идет постоянно файловое сканирование и неправильно работает обработка запросов
## Режимы работы с множественными процессами в Apache
![[Pasted image 20260805172818.png]]
- PreFork - на каждый тип запроса Apache инициализирует процесс (процессор 8 ядер, если apache инициализировал все 8 процессов - мы ждем пока процессы закончатся чтобы нагрузить их снова ), т.е. 1 запрос = 1 процесс 
- Worker - 1 запрос = несколько потоков в 1 процессе
- Event - 1 запрос = 1 поток на несколько соединений, то есть соединений несколько, в каждом есть поток который обрабатывает все процессы

### Процесс работы Nginx
![[Pasted image 20260805173416.png]]
- Синий зеленый и оранжевый это 1-й 2-й 3-й запросы соответственно
- В традиционных серверах на обработку каждого запроса уходит какое-то время и все остальные запросы ждут обработки предыдущих
- В nginx в рамках одного процесса может обрабатывать несколько процессов - он запускает процессы, которые ждут соединения, соединения ждут запросы, nginx запросы обрабатывает и открывает новые соединения - процессы при этом не закрывает

![[Pasted image 20260805173747.png]]
### Как работает Nginx
![[Pasted image 20260805173829.png]]
- Есть управляющий мастер-процесс, который следит за количеством исполнителей (воркеров), их загрузкой и мониторить, чтобы они не залипали
- Есть протоколы:
	- HTTP для общения с Web-server-ом
	- FastCGI для общения с PHP, позволяющий подключаться к PHP, Python, Perl
	- memcache или Redis - встроенный кэшер для nginx-а
- Поддерживает HTTP/HTTPS сообщения
- Внизу у нас есть:
	- загрузчик кэша
	- диспетчер кэша - тот кто управляет - как долго живет кэш, когда его удалять, когда сохранять, чтобы кэш всегда был свежим

- user - от какого пользователя nginx должен работать

	- **`modules-available`**: Хранит конфигурации или файлы всех установленных модулей, которые система может использовать, но не обязательно применяет прямо сейчас.
	- **`modules-enabled`**: Содержит только те модули, которые сервер реально подключает в данный момент.
- events - 
	- worker_connections - количество коннектов, который может обрабатывать 1 воркер
- http - общая настройка http подключения
	- tcp_nopush - конфиг, запрещающий отправку неполных сообщений (TCP  протокол включает)

	- default_type - дефолтный тип 
	- access_log - куда писать логи доступа
	- gzip - архивация включена для запросов, чтобы они занимали меньше места
	- include - подключаем все конфигурационные файлы для обработки http
	- include - подключаем подключенные сайты в конфиге nginx

#### worker_connections
![[Pasted image 20260806101249.png]]
- сколько 1 воркер может обрабатывать соединений
- 1 соединение = пришел запрос - начало соединения - запрос ушел на обработку php-fpm - запрос обработался и вернул ответ nginx - nginx вернул ответ клиенту (соединение = от получения запроса до отправки ответа)
- в основном определеяется оперативной памятью, тк php все обрабатывает оперативной памятью. 
- для подсчета нужного количества мы можем взять сколько всего процессов в worker_process у нас может быть запущено, далее делим оперативную память на кол-во процессов - понимаем сколько в среднем занимает 1 соединение, относительно этого считаем сколько должно случиться соединений, чтобы занять почти полностью всю оперативную память
Пример: есть 2ГБ оперативки, 4 процесса => на 1 процесс выделено 512МБ и если на каждое соединение мы тратим по 5МБ, то в worker_connections мы указываем 100 - кол-во соединений (5 * 100 = 500 МБ =~ 512 МБ - но мы округляем в низшую сторону, дабы не занимать всю оперативку)

##### Контекст location (внутри контекста server)

Необходим для настройки динамики, до этого смотрели только настройку статики
Location сравнивает что к нам пришло (какой идет хвост у домена или параметры запроса), может сравнивать по:
- точному совпадению
- префиксу
- регулярному выражению
- совпадению префиксов
![[Pasted image 20260806145303.png]]
![[Pasted image 20260806165839.png]]

- сервер слушает 80 порт и домен mysite.local
- у него есть рутовая папка 
- все запросы он будет отправлять на index.php либо index.html
-  1 location = для всех запросов с префиксом .jpg, .gif, .css и тд все, что описаны в скобках location мы не записываем это обращение (access_log off), и отдаем этот файл напрямую. expires max - настройка кэша, nginx будет хранить все в кэше и не будет больше ходить на сервер и читать файловую систему, чтобы ответить на запрос верно
- 2 location / = локация ко всем запросам, отправляем их на index.php и отправляем ему query_string 
- 3 location = если у нас приходят все файлики .php, сначала пытаемся его получить - при неполучении отправляем 404 (try_files), разбиваем файлик для fastcgi - парсим путь, передаем его в fastcgi_pass - app:9000 - развернутый php-fpm в docker-е, который работает на порте 9000, fastcgi_index- какой файл индекса в php-fpm, fastcgi_param - передаем все параметры, include - включаем fastcgi_params
