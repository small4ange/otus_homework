# ООП в PHP
Тренды пришедшие из Java:
- все приложение состоит из классов, интерфейсов и трейтов
- классы лежат в файлах (один класс = один файл)
- связанные между собой классы - это пакеты (один пакет = один каталог)

Стажер Вася создает классы для игры
```php
class Paladin  
{  
    public string $name;  
    public int $hp;  
}  
  
class Druid  
{  
    public string $name;  
    public int $hp;  
}  
  
$leeroy = new Paladin();  
$leeroy->name = 'Лирой Дженкинс';  
$leeroy->hp = 100_000;  
  
echo "{$leeroy->name}, {$leeroy->hp}" . PHP_EOL;  
  
$ido = new Druid();  
$ido->name = 'Идо';  
$ido->hp = 150_000;  
  
echo "{$ido->name}, {$ido->hp}" . PHP_EOL;
```
Но для лучшей практики сохраняет классы Druid и Palladin в отдельные файлы, теперь их нужно как-то подключить.
### Подключение классов
```php
include 'Paladin.php';  
include 'Druid.php';
```
 Но если подключать таким образом возникает несколько проблем:
 - много включений в одном файле
 - пути могут поменяться
 - переиспользование одного класса и ошибки из-за этого
 - одинаковые названия классов
### Автозагрузка
Простейший скрипт автозагрузки:
```
spl_autoload_reqister(
	static fn($class) => include "$class.php"
);
```
Регистрируем функцию и если php встречает класс, который ему неизвестен - просто вызываем include этого класса
Похожий более сложный механизм используется в фреймворках PHP

# Основы Composer

Современная разработка не заставляет придумывать веломипед и заново разрабатывать базовые классы для работы с бд и прочим. Для этого существуют различные библиотеки, которые необходимо в проект установить. 
Composer cам по себе необходим для управления библиотеками в проекте и установкой конкретных версий, так как для одних библиотек могут понадобится еще другие библиотеки, которые могут быть несовместимы с теми, которые нужны разработке проекта (это называется граф зависимостей и чаще всего его приходится разгребать руками, что занимает много времени и сил разработчика бедного)

Composer - пакетный менеджер, который работает так:
- мы подключаем Composer к нашему приложению
- говорим ему какие нам нужны библиотеки
- он сам разбирается со всеми нужными зависимостями и конфликтами версий
- после этого скачивает нужные пакеты
- и автоматически генерирует код для автозагрузки (как библиотек так и классов текущего проекта)
#### 1.  Инициализация приложения
```
composer init
```
- в названии (name) рекомендуется использовать префикс пространства имен (otus/test-app)
- тип (type) - project
- остальные поля можно не заполнять

#### 2. Добавление пакетов
- имя пакета берем из документации к пакету
- composer сам выберет подходящую версию
- по умолчанию пакет устанавливается в каталог vendor
- после установки composer добавит классы пакета в автозагрузку и обновит composer.json, composer.lock

Например Slugify
```
composer require cocur/slugify
```

## Добавление пакетов, нужных только во время разработки
```
composer require --dev phpunit/phpunit
```
- эти пакеты будут установлены только локально
- во время деплоя на прод composer эти пакеты просто проигнорит
## Каталог vendor:
- создается автоматически
- в момент установки пакета Composer копирует в него исходный код пакета
- у каждого проекта отдельная копия этого каталога
- этот каталог принято добавлять в .gitignore тк composer может сам установить разработчику все необходимые пакеты, если разработчику передать composer.lock
