# ООП в PHP
Тренды пришедшие из Java:
- все приложение состоит из классов, интерфейсов и трейтов
- классы лежат в файлах (один класс = один файл)
- связанные между собой классы - это пакеты (один пакет = один каталог)

Стажер Вася создает классы для игры
```php
class Paladin  
{  
    public string $name;  
    public int $hp;  
}  
  
class Druid  
{  
    public string $name;  
    public int $hp;  
}  
  
$leeroy = new Paladin();  
$leeroy->name = 'Лирой Дженкинс';  
$leeroy->hp = 100_000;  
  
echo "{$leeroy->name}, {$leeroy->hp}" . PHP_EOL;  
  
$ido = new Druid();  
$ido->name = 'Идо';  
$ido->hp = 150_000;  
  
echo "{$ido->name}, {$ido->hp}" . PHP_EOL;
```
Но для лучшей практики сохраняет классы Druid и Palladin в отдельные файлы, теперь их нужно как-то подключить.
### Подключение классов
```php
include 'Paladin.php';  
include 'Druid.php';
```
 Но если подключать таким образом возникает несколько проблем:
 - много включений в одном файле
 - пути могут поменяться
 - переиспользование одного класса и ошибки из-за этого
 - одинаковые названия классов

### Отличие require от include
- **`require` (Обязательный)**: Если файл отсутствует, PHP выдает **критическую ошибку (Fatal Error)**. Скрипт немедленно прекращает выполнение.
- **`include` (Желательный)**: Если файл отсутствует, PHP выдает **предупреждение (Warning)**. Скрипт продолжает работать дальше. 
### Автозагрузка
Простейший скрипт автозагрузки:
```
spl_autoload_reqister(
	static fn($class) => include "$class.php"
);
```
Регистрируем функцию и если php встречает класс, который ему неизвестен - просто вызываем include этого класса
Похожий более сложный механизм используется в фреймворках PHP

# Основы Composer

Современная разработка не заставляет придумывать веломипед и заново разрабатывать базовые классы для работы с бд и прочим. Для этого существуют различные библиотеки, которые необходимо в проект установить. 
Composer cам по себе необходим для управления библиотеками в проекте и установкой конкретных версий, так как для одних библиотек могут понадобится еще другие библиотеки, которые могут быть несовместимы с теми, которые нужны разработке проекта (это называется граф зависимостей и чаще всего его приходится разгребать руками, что занимает много времени и сил разработчика бедного)

Composer - пакетный менеджер, который работает так:
- мы подключаем Composer к нашему приложению
- говорим ему какие нам нужны библиотеки
- он сам разбирается со всеми нужными зависимостями и конфликтами версий
- после этого скачивает нужные пакеты
- и автоматически генерирует код для автозагрузки (как библиотек так и классов текущего проекта)
#### 1.  Инициализация приложения
```sh
composer init
```
- в названии (name) рекомендуется использовать префикс пространства имен (otus/test-app)
- тип (type) - project
- остальные поля можно не заполнять

## Добавление пакетов, нужных только во время разработки
```sh
composer require --dev phpunit/phpunit
```
- эти пакеты будут установлены только локально
- во время деплоя на прод composer эти пакеты просто проигнорит
## Каталог vendor:
- создается автоматически
- в момент установки пакета Composer копирует в него исходный код пакета
- у каждого проекта отдельная копия этого каталога
- этот каталог принято добавлять в .gitignore тк composer может сам установить разработчику все необходимые пакеты, если разработчику передать composer.lock
## Файл composer.json:
- создается автоматически и дорабатывается вручную
- указывает желаемые версии установленных пакетов
- содержит настройки автозагрузки и необходимые расширения PHP
## Файл composer.lock:
- создается автоматически, лучше не редактировать
- содержит инфу о конкретных версиях установленных пакетов
- файл принято класть в git, чтобы у всех разработчиков был идентичный набор пакетов

## Типичные вопросы с собесов:
- чем отличается composer install от composer update?
composer install доустанавливает пакеты из жестко зафиксированных в  composer.lock, composer update переустанавливает пакеты из composer.json, обновляя их версии до последних и обновляя composer.lock
- чем отличается composer require от composer require --dev
composer require добавляет в composer.json в массив require необходимую библиотеку для прода, а --dev добавляет в массив require-dev необходимую библиотеку для разработки
- нужно ли хранить composer.lock в git?
нужно, чтобы другие разработчики могли установить себе те же версии зависимостей и они были у всех одинаковыми, а сам файл composer.lock обновляя composer update лучше обновлять одному разработчику, кто умеет в случае чего настраивать версии зависимостей

# Разработка пакетов

Есть смысл разработать свой собственный пакет, когда мы:
- хотим его переиспользовать в разных проектах
- пишем библиотеку для работы с публичным API

Разработаем пакет, который будет считать кол-во символов в строке
Создаем приложение
```sh
composer init
```
Записываем Package name 
В Package Type пишем library
>**library** означает переиспользуемый код для других программ, а **project** — готовое к работе приложение

Отказываемся от написания зависимостей 
![[Pasted image 20260731164148.png]]
.gitignore
```gitignore
# PhpStorm files
*.iml
.idea

# Project files
vendor
composer.lock
```
README.md
```markdown
# Процессор строк  
  
Краткое описание пакета  
  
## Требования  
  
- PHP 8.2  
  
## Установка  

composer require dmitry-kirillov/otus-composer-package

## Использование  

<?php  
  
$processor = new StringProcessor();  
echo $processor->getLength('my string')' // 9
```

Создаем на github публичный репозиторий, закидываем туда наш проект:
```sh
git init

git config user.email "dk@example.com" && git config user.name "DmitryKirillov"

git add .

git commit -m "Init commit"

git remote add origin git@github.com:DmitryKirillov/otus-composer-package.git

git push -u origin HEAD
```

**Разработка самого проекта**

```php
class StringProcessor  
{  
    public function getLength(string $s): int  
    {  
        return strlen($s);  
    }  
}
```
И отправляем проект в гитхаб
```sh
git add .

git commit -m "Add StringProcessor"

git push origin HEAD
```
Затем каждое наше приложение должно быть с указанием версии, поэтому версию мы указываем как тег коммита в гите:
```sh
git tag -a 1.0.0 -m "Init version"
```
